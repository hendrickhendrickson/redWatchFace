# Getting this onto a watch

Setting up is **per machine**, and it has been done twice. Everything here was hit in practice; the
traps outnumber the steps, and most of them fail silently.

---

## Prerequisites

Android Studio is _optional_ — the CLI toolchain alone gives a green build. What is actually
required:

1. **JDK 21.** Not 25: Android Studio's bundled JBR is 25 and Gradle 8.11.1's embedded Kotlin
   compiler (2.0.20) dies on it with `IllegalArgumentException: 25.0.2`. Confusingly
   `./gradlew --version` still works, so this looks fine until the first real build. If you use
   Studio, _Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK_ must also
   point at 21.
2. **Android SDK** with `platform-tools` (for `adb`), `platforms;android-36` and
   `build-tools;35.0.0`.
3. **Node ≥ 22.18**, for the generator and the device tooling. `npm ci` at the repo root.
4. Optional: **Android Studio**, for inline WFF XML validation as you type and the emulator GUI.

Staying on `compileSdk = 36` is deliberate: it installs on Wear OS 6 _and_ 7 watches. Going to 37
also needs the AGP pin raised.

The Gradle wrapper **is** committed — `gradlew`, `gradlew.bat` and `gradle-wrapper.jar`, taken from
the Gradle repo at tag `v8.11.1`. It was not generated by an Android Studio sync (only
`gradle-wrapper.properties` was), and `gradle wrapper` cannot bootstrap it either, since there is no
standalone Gradle to run it with.

## Bootstrapping on a fresh machine (no Android Studio, no admin)

Done end-to-end on 2026-08-03 for the second machine. **No Android Studio and no elevation** — the
whole thing lands under `%USERPROFILE%` and `%LOCALAPPDATA%`, and it produced a green validate +
assemble + memory-footprint in about 15 minutes, most of it download time.

```powershell
# 1. JDK 21 — the zip, not the installer (see below)
#    https://github.com/adoptium/temurin21-binaries/releases/download/jdk-21.0.12%2B8/
#      OpenJDK21U-jdk_x64_windows_hotspot_21.0.12_8.zip
tar -xf jdk21.zip -C $env:USERPROFILE\.jdks       # -> ~/.jdks/jdk-21.0.12+8

# 2. Android cmdline-tools -> <sdk>/cmdline-tools/latest  (note the rename)
#    https://dl.google.com/android/repository/commandlinetools-win-13114758_latest.zip

# 3. env, user scope, no admin
[Environment]::SetEnvironmentVariable("JAVA_HOME",   "$env:USERPROFILE\.jdks\jdk-21.0.12+8", "User")
[Environment]::SetEnvironmentVariable("ANDROID_HOME","$env:LOCALAPPDATA\Android\Sdk",        "User")
#    + <jdk>\bin, <sdk>\platform-tools, <sdk>\cmdline-tools\latest\bin on PATH

# 4. packages
sdkmanager --sdk_root=$sdk "platform-tools" "platforms;android-36" "build-tools;35.0.0"

# 5. local.properties (gitignored, so it never survives a clone)
"sdk.dir=C:\\Users\\<you>\\AppData\\Local\\Android\\Sdk" > local.properties

# 6. the two jars — gitignored, so re-download per machine
#    gh release view --repo google/watchface   (or the API; assets are on the `release` tag)
```

**Four things that cost time and will cost it again:**

- **Do not install the JDK with `winget`.** The Temurin package is an MSI, an MSI writes to
  `Program Files`, and that means UAC. In a non-interactive shell the install hangs forever on a
  `consent.exe` prompt nobody can see — it looks like a slow download.
- **`sdkmanager --licenses` cannot be automated by piping `y`.** It reads the console directly, so a
  non-interactive shell leaves it sitting at `Review licenses… (y/N)?` and then reports
  `7 of 7 SDK package licenses not accepted`. Write the hash files into `<sdk>/licenses/` instead —
  `android-sdk-license` holds three SHA1s, one per line.
- **`Expand-Archive` fails on both of these zips**, and its failure handler then spews a screenful of
  `Cannot find path …` from its own cleanup, burying the real error. `tar -xf` is built into
  Windows 10+ and handles both.
- **The two verification jars are gitignored** (`tools/*.jar`), so a clone has the LICENSE files but
  not the jars — and both Gradle tasks then **skip silently**. `onlyIf` logs one `Skipping:` line and
  the build still says `BUILD SUCCESSFUL`. **Check for the `PASSED` / `PASS` lines, not the build
  result.**

Version drift seen against the first machine: cmdline-tools rev 19 (was 22), `adb` 37.0.1. Neither
mattered. The validator must be 1.7.0 or later — that is the one supporting format version 5.

## Build and verify

```powershell
./gradlew :watchface:assembleDebug
./gradlew :watchface:validateWatchFaceXml     # -> PASSED against version #5
./gradlew :watchface:checkMemoryFootprint     # -> PASS
```

`checkWatchFaceXmlUpToDate` runs before `validateWatchFaceXml` and, unlike the two jar-gated tasks,
**throws rather than skips** when the generator is missing — a missing jar is a separate download, a
missing generator is a broken checkout. It does skip, loudly, when a mock is in place, because after
a capture run that is the normal state of the tree.

Both jar tasks were once broken in ways that reported success: `validateWatchFaceXml` printed
`BUILD SUCCESSFUL` over a failing validation because the jar prints `SEVERE` but **exits 0**, and
`checkMemoryFootprint` passed a flag the tool does not have and had no `dependsOn`, so it raced
`assembleDebug`. Both are fixed in `watchface/build.gradle.kts`, and both now use the JDK Gradle runs
on rather than bare `java` from `PATH`.

## Wiring up the Pixel Watch 4

The PW4 charger has **no USB data path**, so this is wireless-only, and **the pairing is per
network** — a new Wi-Fi means pairing again.

1. Watch: _Settings → System → About → Build number_, tap 7×.
2. _Settings → Developer options_ → enable **ADB debugging** + **Wireless debugging**.
3. _Wireless debugging → Pair new device_ → note IP:port + 6-digit code.
4. `adb pair <watch-ip>:<pair-port> <code>` — the code can be passed inline, which avoids the
   interactive prompt. Then `adb connect <watch-ip>:<debug-port>`. **The pair port and the debug port
   are different**, and the pair port changes every time you reopen the dialog.
5. The watch then appears **twice** in `adb devices`: as `<ip>:<port>` and as
   `adb-<serial>._adb-tls-connect._tcp` (mDNS). Same device. **Prefer the mDNS name** — the port
   changes whenever the watch sleeps, so the IP entry goes stale while the mDNS one keeps working
   (`adb mdns services` re-resolves it). Pin it, or `installDebug` installs to every connected device
   including the emulator:
   ```powershell
   $env:ANDROID_SERIAL = "adb-66021WRCVW20GK-QnLLgW._adb-tls-connect._tcp"
   ```
6. `./gradlew :watchface:installDebug`
7. Activate without touching the watch:
   ```powershell
   adb shell am broadcast -a com.google.android.wearable.app.DEBUG_SURFACE `
     --es operation set-watchface --es watchFaceId de.redplant.watchface.blob
   ```
   A successful activation replies `result=1 ... Runtime=[2]` (2 = the WFF runtime). If `adb devices`
   says `unauthorized`, `adb kill-server && adb start-server`.

**`result=1 ... Runtime=[2]` means "a face with that id is now active", not "your new build is
running".** The activation broadcast succeeds against whatever build is already installed — do not
read it as confirmation that an install worked.

This watch is **Wear OS 7 / API 37** (`ro.build.version.release=17`, `sdk=37`, `meridian_btwifi`) and
its display is **426 × 426**, not the 456 the XML header once claimed. The 450 design canvas
therefore scales _down_ ~0.95, and the emulator's 454 renders everything ~6% larger than the wrist.

### A new machine cannot update the watch's existing install

```
INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package de.redplant.watchface.blob
signatures do not match newer version; ignoring!
```

Nothing is wrong. A debug APK is signed with `~/.android/debug.keystore`, that keystore is generated
per machine, and Android will not let a differently-signed build replace an installed package.

```powershell
adb uninstall de.redplant.watchface.blob
./gradlew :watchface:installDebug
```

Nothing is lost — a watch face has no user data. Copying `debug.keystore` between machines would also
work and would avoid the uninstall.

## The emulator

Useful for layout, useless for weather and health. Create a **Wear OS / API 36** round AVD; two
gotchas:

- For API 36+ the only Wear image is tagged **`android-wear-signed`**, not `android-wear`:
  `system-images;android-36;android-wear-signed;x86_64`.
- That image ships no `devices.xml`, so `avdmanager` errors on it and **silently fails to apply the
  round shape** — `config.ini` comes out with `hw.lcd.circular=false`. Set it to `yes` by hand, or
  any bezel check is meaningless. The boot log should show `androidboot.emulator.circular=1`.

What cannot be checked there:

- **The clock cannot be set.** `android-wear-signed` is a production `user` build
  (`ro.debuggable=0`), so `adb root` is refused.
- **Weather will never resolve.** `adb emu geo fix` returns `OK`, but logcat shows
  `WeatherDataSyncerV2: Unable to fetch Location` — the gps provider is `ProviderRequest[OFF]` with
  only passive listeners, so nothing consumes the injected fix. Treat `--°` as the expected emulator
  state.
- **Heart rate and steps cannot be simulated.** `USE_SYNTHETIC_PROVIDERS` switches the HAL, but the
  only synthetic actions registered are `FALL_OVER`, `START_SLEEPING` and `STOP_SLEEPING` — there is
  no `START_WALKING`.

## Capturing and reviewing states

Two tools, and they answer different questions:

```powershell
node tools/capture-states.ts                       # photograph every state into docs/states/
node tools/capture-states.ts --only=cold,gloves
node tools/capture-states.ts --sheet-only          # rebuild the contact sheet

node tools/cycle-states.ts                         # show every state on the wrist, looping
node tools/cycle-states.ts --laps=1
node tools/cycle-states.ts --only=rainy,thunderstorm,nightfull
node tools/cycle-states.ts --restore               # recover after a hard kill
```

`capture-states.ts` photographs states; `cycle-states.ts` **shows** them, every one mocked `--live`
so the accelerometer and the clock stay real. **Nothing that moves can be judged from a screenshot or
from the validator** — parallax, the Zzz drift, the falling rain, the sweat drips and the ambient
crossfade are all invisible in a still. Three features once shipped broken for exactly this reason,
and `cycle-states.ts` exists because of it.

Underneath both is `tools/mock-state.ts`, which patches the **data** — temperature, heart rate, hour
— and lets the real `Condition`s evaluate, so nesting takes care of itself: set the temperature to 0
and both the cold and the freezing branches fire. It takes `--set=KEY=VALUE` for points _between_ the
named states (`--set=HEART_RATE=150`), and unknown keys abort rather than silently leaving the source
live.

> **`mock-state.ts off` restores `watchface.xml` but does not reinstall.** After a capture run the
> watch is normally still on a mock, which pins the clock sources, zeroes the accelerometer and swaps
> `<DigitalClock>` for a static `PartText`. That combination once produced three separate bug reports
> — "the z's have gone slow", "the parallax has vanished", "ambient is in the wrong font weight" —
> none of them in the watch face. `mock-state.ts status` inspects the **working tree** and cannot see
> the device.

### Three ways the capture script lied

All three produced files that looked like successful captures. Read this before trusting any future
sweep, and before simplifying the capture tooling.

1. **The screen dimmed mid-sweep and two states came back as ambient frames.** The wake step only
   sent `KEYCODE_WAKEUP`, which does nothing to the display timeout, and the validation at the time
   was "bright somewhere, and mostly dark" — which is _exactly_ the signature of a thin-white-on-black
   AOD frame. Fixed by holding the timeout open across the loop **and** adding a colour test: ambient
   is strictly greyscale, and the face has a coral heart and a green battery gauge, so chroma
   separates them where brightness cannot.
2. **Restoring the screen timeout silently left the watch never sleeping.** The first version of that
   fix read the "previous" value in two places and restored in two. Wireless debugging drops
   constantly, one restore hit a moment when the device lookup returned nothing, and the next section
   read the elevated 600000 as its original and faithfully put that back. Now: exactly one read,
   exactly one restore, retried and verified, and a guard that refuses to adopt any value ≥ 300000.
3. **A capture can land mid ambient crossfade.** Wear OS drives AOD from wrist-down detection, **not**
   from `screen_off_timeout`, so holding that setting open stops the screen blanking but not dimming.
   The resulting frame — blobs already faded, umbrella canopy not yet — is the worst kind of bad
   capture, because it looks like a deliberate design decision. Caught by measuring:

   | frame              | max | lit%  | sat%     |
   | ------------------ | --- | ----- | -------- |
   | good states        | 247 | 10–11 | 4.3–5.9  |
   | mid-transition     | 217 | 3.72  | 1.49     |
   | dimmed-but-not-out | 255 | 7.31  | 2.99     |
   | true ambient       | 217 | 2.37  | **0.00** |

   `max` is the sharp discriminator: an undimmed frame renders cream `#fff6e8` at luminance **247
   exactly**, and any dimming drags it down. The thresholds in the tooling are those measurements,
   not guesses.

A fourth arrived later: **a dimmed frame passed the guard** when the test was `max luminance >= 240`,
because the watch draws a small pure-white system indicator that pins `max` at 255 however dark the
face is. The test is now the _fraction_ of pixels over luminance 200 — 3.7–5.3% good, 0.3% dimmed.
**Probe a pixel; do not trust the guard.**

`ENTER_AMBIENT` does **not** work for capturing AOD: the broadcast is accepted but the display will
not dim a screen that was just woken, and capturing requires waking it.

### Device traps that are not about the face

- **`KEYCODE_WAKEUP` does not wake the watch out of AOD.** With always-on display the screen is
  already on (`dumpsys power` reports `mWakefulness=Dozing`), so the keyevent is a no-op and every
  capture comes back ambient. **A tap wakes it**: `input tap 213 213`. Send it _after_ the
  `set-watchface` broadcast, so the face is the foreground surface — this face declares no
  `ComplicationSlot`, so a tap on it does nothing, whereas a tap on the launcher opens an icon.
- **`KEYCODE_HOME` toggles.** From the face it opens the launcher; from the launcher it returns. It
  is the _fix_ when a capture comes back wrong, not something to send pre-emptively — sending it
  before every capture is what produced a whole run of app-icon grids. `KEYCODE_BACK` does not get
  out of the launcher, and neither does an edge swipe. Verify the frame instead: the face is almost
  entirely black, so a lit-pixel fraction above ~14% means something is covering it.
- **A notification chip can land on the face** and no check can tell it from the face.
  `cmd notification snooze --for <ms> '<key>'` parks it for a sweep; `unsnooze` restores it. Do not
  confuse it with the small white unread dot, which is in most frames.
- **`dumpsys battery set` survives a disconnect.** If wireless debugging drops mid-session the watch
  is left reporting a fake battery level indefinitely. Always finish with `dumpsys battery reset` and
  check it landed. If you do force a level, use one well clear of the low-battery threshold — Wear OS
  enables battery saver and draws its own indicator, and `BATTERY_IS_LOW` flips the face's battery
  text to coral, none of which is the state under review.
- **A hard kill skips `finally`.** Killing the job that owns `cycle-states.ts` leaves the watch on a
  short timeout running a mock. `--restore` recovers from the state file and **verifies by comparing
  the installed APK's md5 against the clean build** — the only check here that cannot be fooled.

### Re-shooting `preview.png`

`res/drawable/preview.png` is **required** — `watch_face_info.xml` references it as
`@drawable/preview`, and removing it fails `aapt` with `resource drawable/preview not found`. It is a
real screenshot, staged via `mock-state.ts on baseline`.

**`adb exec-out ... > file.png` corrupts the PNG in PowerShell.** `>` is not a byte pipe: it decodes
the stream as text and re-encodes it, prepending a UTF-8 BOM — the file starts `ef bb bf ef bf bd 50 4e`
where a PNG must start `89 50 4e 47`. Since `aapt` only needs _a_ file at that path, a corrupt one
gets quite far before anything complains. Verify the header, not the file size.

```powershell
adb shell screencap -p /data/local/tmp/preview.png
adb pull /data/local/tmp/preview.png watchface/src/main/res/drawable/preview.png
```

Two things for the next re-shoot: the heart rate blinks to `--` between sensor reads and a preview
showing `--` reads as broken, so capture in a short retry loop and keep the frame where the HR box
contains cream `#fff6e8` rather than placeholder `#c3b1a4`; and the watch must be tapped awake first.

## What the wrist confirmed that nothing else could

- **Heart rate and steps render with all three `android.permission.health.*` grants reading
  `granted=false`.** No prompt appears and none is needed — the WFF runtime reads the sensors and
  feeds the declarative face, which has no code of its own. The `uses-permission` lines are kept in
  case another watch or OS version gates on them.
- **`BATTERY_IS_LOW` fires around 6–8%**, and both the `%` text and the icon's fill bar render coral.
  Wear OS paints its own low-battery mark near the bottom edge, which is not part of the face.
- **Outdoor legibility at 3000 nits is fine.** The question was half-answered by the dark redesign —
  the face is cream-on-black, not navy-on-cream.
